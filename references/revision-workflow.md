# 推敲ワークフロー

小説の推敲（revision）は、以下の3段階で行う。

**推敲時の情報取得原則**: 推敲でも vecmemori（fact_store）を一次情報取得手段として使用する。矛盾検出（contradict）・キャラ情報取得（probe）・伏線確認（search）はすべて vecmemori で完結する。.md ファイルの全読みは不要。.md は差分検出・詳細確認時にピンポイントで読む。

| Phase | 名称 | 視点 | タイミング |
|-------|------|------|-----------|
| A | プロット検証 | ミクロ（構造） | 本文執筆前 |
| B | 整合性検証 | ミクロ（細部） | 本文執筆後 |
| C | 読者視点評価 | マクロ（体験） | 整合性検証後 |

## コンテキスト管理（必須）

長文の小説プロジェクトでは、会話の継続とともにエージェントのコンテキストウィンドウが逼迫し、応答品質が低下します。以下のタイミングで必ず `/compress` を実行してください。

### 実行タイミング

| タイミング | 説明 |
|-----------|------|
| **フェーズ移行時** | 企画→プロット推敲→執筆→校正の各フェーズ切替時に `/compress` を実行 |
| **会話が長くなったと感じたとき** | エージェントが自覚的に判断し、ユーザに `/compress` 実行を提案する |
| **ユーザが明示的に要求したとき** | ユーザから「圧縮して」等の指示があった場合は即座に実行 |

### 提案の仕方

```
会話が長くなってきました。`/compress` でコンテキストを整理しませんか？
以降の応答が安定します。
```

ユーザの返答を待たずに `/compress` を実行してはいけません。必ず提案→承認を得てから実行してください。

```bash
# インストール
git clone https://github.com/kgmkm/hermes-fake-moa.git ~/.hermes/skills/hermes-fake-moa
```

## Phase A: プロット検証（本文執筆前）

本文を書く前に、プロット自体の整合性を検証する。

### A-1. タイムライン検証

各章の日付・時刻・季節を書き出し、矛盾がないか確認する。

```
序章: 大正12年 晩夏 1日目〜3日目
  1日目 夕方: 灯と九十九の出会い
  2日目: 狐火の渓谷
  2日目 夜: 両親死亡
  3日目 朝: 九十九が灯を里に返す
第1章: 昭和8年 初秋（10年後）
  ...
```

### A-2. キャラ知識状態チェック

各シーンの冒頭で、キャラクターがその時点で「何を知っていて、何を知らないか」を明記する。

```
Scene 2: 灯が九十九の社を再訪する
- 灯の知識: 九十九がこの山に棲むと知っている。両親が殺された真相は知らない。
- 九十九の知識: 灯が退魔師になったことは知らない。灯の顔を覚えていない。
```

これにより、キャラが知らないことを言わせてしまうミスを未然に防ぐ。

### A-3. 伏線整合性チェック

全章の伏線を一覧にし、張り→回収の対応が取れているか確認する。

```
伏線: 蛍の墓 → 張り:序章 / 回収:第3章
伏線: 「また、あえる？」 → 張り:序章 / 回収:第3章
```

### A-4. プロット推敲チェックリスト

Phase A の最後に、以下の全項目を満たしているか確認する。1 項目でも未完了の場合は先に進まない。

| # | チェック項目 | 検証方法 |
|---|------------|---------|
| 1 | タイムラインに矛盾がないか | A-1 |
| 2 | 各キャラの知識状態が明確か | A-2 |
| 3 | 伏線の張り→回収が対応しているか | A-3 |
| 4 | 後の章で重要な役割を持つ存在（モブ・地名・物品等）が、それ以前に登場・言及されているか | A-3 の拡張 |
| 5 | キャラの台詞が、その時点の知識状態に基づいているか | A-2 の適用 |
| 6 | 時代設定に合わない語彙がプロットのキー台詞に含まれていないか | planning-workflow 1-2 の「世界制約リスト」に照合 |

## Phase B: 整合性検証（本文執筆後）

ミクロ（細部）のチェック。論理・語彙・数値・五感の不備を潰す。

### B-1. 対話チェーン検証

台詞を書いた後、以下の3点を確認する：

1. この台詞の論理的前提は何か？
2. その前提は物語中で確立されているか？
3. 話者はその前提を知りうる立場か？

例：
```
九十九「おまえは、あの女に、よく似ていた——」
灯「……私は、あなたの——代わりだったんですか」 ← 問題
```
「あなたの代わり」の指示対象が「500年前の女性」だが、灯はこの場で初めてその話を聞いた。論理的前提が未確立。

修正案：灯が直接受けるべき感情に変更する。
```
灯「……だから。私を——守ってくださったんですか」
```

### B-2. 指示語の射程チェック

対話中の指示語（これ/それ/あれ/その/あの/あなたの）を抽出し、指示対象を明示的に確認する。

| 指示語 | 出現箇所 | 指示対象 | 問題 |
|--------|----------|----------|------|
| あなたの | 第3章「あなたの代わり」 | 九十九 | → 九十九本人を指すが文脈上不適切 |

### B-3. 世界制約チェック

プロジェクトの世界観に存在しない語彙・概念を使っていないか、台詞と地の文を照合する。

**チェック方法：**
1. `fact_store(search, query="世界制約 存在しない")` で制約リストを vecmemori から取得（.md 読込は初回のみで十分）
2. 本文完成后、全台詞を一行ずつスキャンし、リストと照合する
3. 現代語・外来語・時代錯誤表現を検出する
4. 制約リストが vecmemori に未登録の場合は `worldbuilding/制約リスト.md` を読んで補完する

**検出パターン：**
- 時代設定がある作品で現代の外来語を使う（例：「ばいばい」「オッケー」「スマホ」）
- 舞台の文化台の文化圏に存在しない概念を使う（例：中世ファンタジーで「コード」「バグ」）
- キャラの知識範囲外の語彙を使う（例：山育ちの少女が化学用語を使う）
- 時代錯誤の比喩（例：大正時代の作品に「記憶が巻き戻る」—— VTR 由来の表現は昭和後期以降）

### B-4. 章間事実整合性チェック

vecmemori の `contradict` を使って、章をまたぐ事実の整合性を検証する。

```python
# 殺害人数の整合性
fact_store(action="contradict", statement="九十九は20人殺した")

# キャラの年齢整合性
fact_store(action="contradict", statement="灯は16歳で鋼は48歳")

# タイムライン整合性
fact_store(action="contradict", statement="灯の両親は灯が社にいた2日目の夜に死亡した")
```

### B-5. 五感ローテーション確認

各シーンで視覚以外の感覚（聴覚・触覚・嗅覚）が2つ以上使われているか確認する。不足している場合は追記する。

## Phase C: 読者視点評価（テーマ・感情・読後感）

マクロ（体験）の評価。Phase A・B がミクロな整合性チェックであるのに対し、読者視点評価は「この作品を読んでどう感じたか」という読者体験の質を問う。

### 問いかけの軸

1. **読後感**: 読んで良かったと思える内容だったか？ 心に残る場面はあったか？
2. **テーマ表現**: proposal.md のテーマ・モチーフが表現できているか？
3. **感情曲線**: 提案された感情曲線通りに感情が動かされたか？
4. **改善提案**: テーマをより深めるために、シーンの構造変更やキャラの行動変更の提案があるか？

### チェック方法

横並び比較推敲の一部として実施する（後述「横並び比較推敲」参照）。各エージェントに以下のプロンプトを与える：

```
あなたは一読者です。この小説を読み、以下の質問に答えてください:
1. 読んで良かったか？ どの場面が心に残ったか？
2. 提案されたテーマ（『恩と正義の相克』『人と妖の境界』『守るということ』）が表現されていたか？
3. 感情曲線通りに感情が動かされたか？
4. テーマをより深めるために改善できるシーンや行動の変更はあるか？
```

ユーザから特定シーンの改善案が出た場合は、その案の妥当性も横並び比較で審議する：

```
以下の改善案について、テーマ深化・感情曲線・読後感の観点から
妥当性を審議してください: [ユーザの提案]
```

## 推敲時の vecmemori 活用

```python
# 章間の矛盾検出
fact_store(action="contradict", statement="確認したい命題")

# キャラの全情報を確認
fact_store(action="probe", entity="灯")

# 伏線の状態確認
fact_store(action="search", query="伏線 未回収")

# 世界観の確認
fact_store(action="search", query="世界観 時代 設定")
```

## 推敲時の Hermes Agent ツール活用

| ツール | 用途 | 使いどころ |
|--------|------|-----------|
| `fact_store(search)` | 設定検索 | 世界観・伏線・キャラ情報を vecmemori から取得（一次手段） |
| `fact_store(probe)` | キャラ全件取得 | キャラの全バージョン・全情報を一括確認 |
| `fact_store(contradict)` | 矛盾検出 | 章間の事実矛盾を自動検出 |
| `session_search` | 過去セッション検索 | 過去の執筆セッションで議論した設定・決定事項の呼び出し |
| `web` | 時代考証・語彙検証 | 「昭和8年 俗語」「大正 度量衡」等でリアルタイム検証 |
| `browser` | 参考資料閲覧 | スタイルガイド・歴史文献・語彙データベースの参照（必要な場合のみ） |

## 横並び比較推敲

推敲は「論理整合性」「文体品質」「時代正確性」「読者体験」と複数の軸があるため、複数モデルの横並び比較によるチェックが有効です。

詳細な手順・コマンド・例外処理は `references/moa-manual-orchestration.md` を参照。以下は概要です。

### 有効化のタイミング

Phase A（プロット推敲）または Phase B（本文推敲）の直前に、ユーザに横並び比較の有効化を提案します。

### モデル選択（4 エージェント構成）

各エージェントに**異なる LLM** を割り当てます（同一モデルでの複数視点は比較の意味を損なう）。

| # | 視点 | 役割 | チェック内容 |
|---|------|------|-------------|
| 1 | 論理整合性 | プロット・伏線・キャラ行動の矛盾検出 | 時間軸、設定数値、因果関係、未回収伏線 |
| 2 | 文体・表現技法 | 比喩・五感・リズム・文体一貫性 | クリシェ、五感充足、説明的モノローグ、文長バランス |
| 3 | 時代考証・語彙 | 時代語彙・風俗検証 | 外来語、俗語、度量衡、学術用語 |
| 4 | 読者体験・ブラッシュアップ | 没入感・感情曲線・余韻評価 | 説明不足/過剰、共感阻害、幕切れ強度、Phase C の問いかけ |

### 実行

`hermes chat -q -m MODEL --provider PROVIDER` による手動オーケストレーション、または `hermes-fake-moa` の `multi-chat.py` による並列実行を使用します。ビルトインMoA（集約型）とは異なり、各モデルの生回答を保存して人間が比較判断します。

### 横並び比較集計

1. 4 エージェントの全指摘を統合
2. 複数モデルが共通して指摘した項目を最優先
3. **【必須】集約した改善案の設定矛盾検出** — 改善案が作品の既存設定（年表、尾の本数と年齢の関係、キャラ過去、世界観ルール）と矛盾していないか照合する。LLM は設定の全体像を把握していないため、改善案に設定違反が混入しうる。矛盾があれば修正またはユーザに代替案を提示
4. 最終修正リストをユーザに提示し、承認を得てから本文修正に着手

### 例外処理

横並び比較実行中に LLM が以下の状態になった場合：

| 現象 | 対応 |
|------|------|
| タイムアウト（600s） | ユーザに「どのモデル・視点・現象」を報告。代替モデル指定 or スコープ縮小を仰ぐ |
| モデル名エラー（404 等） | ユーザに正しいモデル名の確認を依頼 |
| 調査拒否・空応答 | ユーザに報告。別モデルで再実行 |

**禁止事項**: 自動リトライ、ユーザに黙ったままの代替モデル選択、エラーを無視した集計。
