# MoA 手動オーケストレーション — 小説推敲の 4 視点横並び比較（エージェント非依存）

`revision-workflow.md`「横並び比較推敲（MoA）」の実行手順。専用ツールが無い環境でも、「別モデルに同じ指示を投げ、結果を集めて比較する」だけで成立する。

ここでいう MoA は**横並び比較**であり、モデル間の合議（アグリゲータ）は行わない。共通指摘の抽出と採否の判断は、実行者（エージェントまたは人間）の仕事である。

## 原則

- **4 視点 × 異なるモデル**。理想は 4 モデル、最低 2 モデル。同一モデルで視点だけ変えるのは「掛け違いによる拾い漏れ防止」であり、比較の意味は薄い
- レビュアーにはプロンプトだけでなく**本文と文脈パック**を渡す。設定の全体像を知らないモデルの指摘は、設定違反の改善案を含む
- 指摘には必ず「場所・改善案（具体的文章）・優先度」を付けさせる（本ファイル「3. プロンプトテンプレート」）
- 評価系（視点 4）は「はい/いいえ＋根拠」を必須とし、根拠のない回答は集計から除外する

## 1. レビュアーに渡すもの

| 渡すもの | 中身 |
|---|---|
| 本文 | `novel/chNN.md`（推敲対象の全章） |
| 文脈パック | `.context/chNN.md`（対象章すべて）※キャラ・制約・伏線・established・制作ログが入っている |
| 作品の憲法 | `AGENTS.md`（文体規則・禁止事項） |
| 索引 | `validate.py --index` の出力（ID ↔ 名称の照合） |

- ツールを持つエージェント（CLI 型）をレビュアーにするなら、ファイルを貼らずに「`<project>` を読んで推敲せよ」とディレクトリを指すだけでよい
- **投げる前に再生成**: `validate.py → pack.py`。古いパックは古い設定のまま指摘させることになる

## 2. 実行パターン

### A. エージェント CLI の非対話モード（推奨）

| エージェント | 例 | 備考 |
|---|---|---|
| Hermes | `hermes chat -q "…" -m <model> --provider <provider> -Q --max-turns 4` | 長文は `--query-file prompts/01_logic.md`（シェル解釈なしで安全） |
| opencode | `opencode run -m <provider/model> "…"` | `--dir <project>` で作業場所、`-f` でファイル添付 |
| Claude Code | `claude -p "…"` | `--model` 等で指定 |
| goose | `goose run -t "…"` | モデルは設定で切替 |

フラグは各ツールの `--help` で確認する。**長いプロンプトはファイル経由で渡す**（コマンドライン長の制限と引用符事故を防ぐ）。

4 視点を別モデルで並列に投げ、結果を `reviews/` に集める例:

```bash
mkdir -p reviews
rev() { hermes chat --query-file "prompts/$1.md" -m "$2" --provider "$3" -Q > "reviews/$1.md" 2>&1; }
rev 01_logic  <model-a> <provider-a> &
rev 02_style  <model-b> <provider-b> &
rev 03_era    <model-c> <provider-c> &
rev 04_reader <model-d> <provider-d> &
wait
```

他エージェントを使う場合は `rev()` の中身を差し替える（例: `opencode run -m "$2" --dir <project> "$(cat prompts/$1.md)"`）。プロンプトファイル名と視点名を揃えておくと集計が楽。

### B. エージェントを跨ぐ

CLI が 1 本しか無くても、書く側と読む側を別エージェントにすれば独立性が上がる（例: 本文は opencode、視点 1・2 は Hermes、視点 3・4 は goose）。

### C. サブエージェント機能（モデルを指定できる場合のみ）

エージェントが「別モデルを指定できるサブエージェント」を出せる場合、視点ごとに投げて回収する（例: Hermes の delegate 系、Claude Code のサブエージェント）。

**注意**: 親モデルを継承する設定のまま投げると同一モデル比較になり、MoA の意味が消える。モデル指定の可否を先に確認する。

### D. 同一エージェント逐次（最終手段）

同一モデルで 4 プロンプトを順に実行する。比較にはならないが、視点の掛け違いによる拾い漏れ防止にはなる。視点ごとに新しいセッションを立てると、前の視点の指摘への引きずられを防げる。

### E. 推敲支援ツール（あれば）

- Hermes 環境: **hermes-fake-moa**（モデル一覧 → パネル登録 → 並列実行 → 結果集約。手順は同スキルの SKILL.md）
- 他環境: 同等の並列実行ツールがあれば同様に使う

## 3. プロンプトテンプレート

### 全視点共通の必須要件

1. 改善案は**修正後の具体的な文章**で書く（指摘だけの回答は無効）
2. 場所は 章・節・行（該当テキストを引用）
3. 優先度（高/中/低）
4. 視点 4 は「はい/いいえ＋根拠」形式。根拠のない回答は集計から除外

### 視点 1: 論理整合性

```
以下の日本語小説の全章を精査し、論理整合性の問題を指摘せよ。
各指摘には必ず改善案（修正後の具体的文章）を添えること。

参考: .context/chNN.md（章ごとの文脈パック。キャラ・伏線・established はここから取得）

チェック項目:
1. 時間軸の矛盾
2. 設定数値の不整合
3. 未回収の伏線
4. キャラ行動の不自然さ

形式: 【章・節】【行】【問題点】【改善案（具体的文章）】【優先度】
```

### 視点 2: 文体・表現技法

```
以下の日本語小説の全章を精査し、文体と表現技法の問題を指摘せよ。
各指摘には必ず改善案（修正後の具体的文章）を添えること。

参考: AGENTS.md（作品の文体規則）

チェック項目:
1. クリシェ（陳腐な比喩・決まり文句）
2. 五感の偏り（視覚偏重。シーンごとに視覚以外の感覚が 2 つ以上あるか）
3. 説明的モノローグ（内面を説明しすぎていないか）
4. 文体の一貫（三人称過去形、キャラの口調・一人称）
5. 文長のリズム（同じ長さの文が続いていないか）

形式: 【章・節】【行】【問題点】【改善案（具体的文章）】【優先度】
```

### 視点 3: 時代考証・語彙

```
以下の日本語小説の全章を精査し、時代考証と語彙の問題を指摘せよ。
各指摘には必ず改善案（修正後の具体的文章）を添えること。

時代設定: （worldbuilding の content から持ってくる）
禁止語彙・知識範囲: 文脈パックの「世界観制約」を参照

チェック項目:
1. 時代に存在しない語彙・概念（外来語、戦後俗語、現代技術用語）
2. 舞台の文化圏に存在しない概念
3. キャラの知識範囲を超える語彙（constraints の unknown_to）
4. 度量衡・通貨単位の時代整合性
5. 時代錯誤の比喩（後世の技術に基づく表現。例: 「記憶が巻き戻る」＝ VTR 由来）

形式: 【章・節】【行】【問題語彙】【時代的理由】【改善案】【優先度】
```

### 視点 4: 読者視点評価

```
あなたは一読者です。以下の小説を読み、以下に答えてください。
全項目「はい/いいえ＋根拠」形式を必須とする。根拠のない回答は集計から除外する。

1. 心に残った場面はどれか。それは物語の冒頭・前半の終わり・後半の終わり・結末のどれに当たるか
2. テーマは表現されていたか。台詞で説明されていた箇所があれば引用せよ
3. 章ごとに感情の強さを 0〜100 で採点せよ（各章に数値と根拠）
4. 次の 6 問に答えよ（各問、はい/いいえ＋根拠）:
   a. 主人公に強い動機があるか
   b. 主人公は開始時点で負け犬か（敵対側の総和が主人公より強いか）
   c. 各シーンに目的・衝突・変化のどれかがあるか
   d. 心に残る場面は、冒頭／前半の終わり／後半の終わり／結末のどこかにあるか
   e. 決着後を引き延ばしていないか
   f. テーマが台詞で説明されず、人物の行動で表現されているか
5. テーマをより深めるためのシーン構造・人物行動の変更案（修正後の具体的な文章で）
```

## 4. 集計

1. 全指摘を統合する。**複数モデルが共通して指摘した項目を最優先**。単独モデルの独自発見も重要度に応じて採用
2. 改善案を横断比較し、最も効果的な案を選定または合成する
3. **【必須】改善案の設定矛盾検出** — 改善案が既存設定（年表・versions・established・世界観ルール）と矛盾しないか、パックで照合する。LLM は設定の全体像を把握していないため、設定違反が混入しうる
   - 実例: 名前の由来の改善案「九つの尾を持ちながら」→ 設定では 50 年で 1 尾、500 年前の若い妖狐は 2〜4 尾。矛盾検出により「いつか九つの尾を揃える日を夢見る」に修正
4. 最終修正リストをユーザに提示し、**承認を得てから**本文修正に着手する（TOML を勝手に改変しない）
5. 採用しなかった改善案は `production-log.toml` に `kind = "reject"` で記録する（同じ案の再提案を防ぐ）。採用で既定の決定を変えた場合も同じく記録
6. 修正後の確認: `check_prose.py` → `validate.py` → `pack.py` 再生成

## 5. モデルの選び方

- 料金・ラインナップは変動が早い。**この文書に固定のプロバイダ一覧を持たない**。エージェントに最新のネット反応を検索させるのが確実（README「LLM にこだわろう！」）
- 視点ごとにモデルを変える。最低 2 モデル、できれば 4 モデル
- 定額プロバイダを優先すると、コストを気にせず 4 本回せる
- 推敲に超安価モデルは向かない。特に視点 1（論理）と視点 4（読者）はモデルの地力が出る
- モデル一覧の取得: Hermes なら hermes-fake-moa の `list-models.py`（全プロバイダ横断）。他環境は各ツールの一覧コマンド、またはエージェントに「利用可能なモデル一覧を出して」と聞く

## 6. 本文がまだ無いとき（プロット診断）

本文ゼロでも `proposal.md`＋plot TOML で横並び診断を回せる。planning §7 の承認条件。章を全部書いてから構造不全に気づく事故を防ぐ。

- 渡すもの：`proposal.md` 全文、対象章の plot TOML（全章）、`validate.py --index` の出力。本文・文脈パックは無い
- 問うのは revision Phase A-5 の 6 問（全巻構造チェック）。文体・時代考証の視点は回さない（本文が無いため）
- 複数モデルが共通して指摘した項目を最優先に採用する。単独モデルの指摘は不採用（§4 の集計1と同基準）
- 共通指摘は章単位ではなく全巻共通の設計問題に集約されることが多い（例：敵対勢力が制度で人格がない、同型解決の反復）。該当章ではなく proposal・chara・plot 全体に戻す
- 採用・却下は `production-log.toml` に記録する（§4 の集計5と同基準）。改訂は revision Phase A-6 の巻き戻し手順で行う
